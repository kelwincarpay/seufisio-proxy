# Atualização da skill `seufisio` — edição de plano recorrente

Instruções para atualizar a skill do OpenClaw (`OPENCLAW-SKILL.md`) com a leitura nova e a
edição de plano recorrente. Complementa `ATUALIZACAO-SKILL-OPENCLAW.md`, que introduziu as
seções 16 a 21.

**Ainda não está em produção.** O código está no PR
https://github.com/kelwincarpay/seufisio-proxy/pull/1 (branch `feat/001-editar-plano-recorrente`).
Só atualize a skill depois do merge e do deploy, senão o agente vai chamar uma rota que
ainda responde no formato antigo. Spec completo em `docs/plano-recorrente-api.md`.

O conteúdo em inglês é para colar direto na skill. O preâmbulo e as notas em português são
só para você.

---

## O que muda, em uma frase por bloco

1. **`GET /api/plans/recurring/:id` mudou de forma.** Não pede mais `cliente_id`, e a
   resposta é um objeto normalizado novo, com limite semanal, dia de vencimento e desconto.
   A seção 17 atual **é substituída inteira**.
2. **Editar plano recorrente** — nova seção 22. Um `PUT` troca grade, serviço, valor,
   desconto e dia de vencimento num request só, com validação de limite semanal antes de
   gravar.
3. **O agente é orientado, não bloqueado, sobre turma cheia** e **é bloqueado, sem
   override, sobre excesso de dias.** Mesma filosofia da venda.

## Quatro conceitos que a skill precisa entender

**Limite semanal vem do nome do serviço.** "Pilates 2x na Semana" → `limite_semanal: 2`.
Se o nome não segue o padrão, o limite é `null`, a resposta traz `aviso`, e o proxy não
valida a quantidade de dias. O agente deve avisar o usuário nesse caso.

**`dias` substitui a grade inteira.** Não é merge. Para mudar só a terça de um plano
"terça e quinta", o agente manda terça nova **e** quinta como está.

**`lotado` é aviso, não bloqueio.** `true` significa que a turma está cheia, mas a edição
já foi gravada. No `GET` vem sempre `null`, porque a leitura não consulta a agenda.

**`dia_vencimento` é só o dia da cobrança.** Não mexe em renovação nem em data de
encerramento; esses dois campos não são editáveis pela skill.

### 17. Get Recurring Plan

Read a recurring plan: service, weekly grid, monthly value, discount, billing day and the
weekly session limit.

**Request:**
```
GET {{SEUFISIO_PROXY_URL}}/api/plans/recurring/125
Authorization: Bearer {{SEUFISIO_API_TOKEN}}
```

**Parameters:**
| Param | Type | Required | Description |
|-------|------|----------|-------------|
| planId | number | Yes | Plan ID (path) — the `id` returned by `POST /api/plans` or listed in `GET /api/clients/:id/sales` with `tipoVenda: servico_recorrente` |
| raw | `1` | No | Query. Appends the raw SeuFisio object in `raw`. Debug only, never show it to the user |

`cliente_id` is **no longer accepted**. The plan is read by its own id.

**Response (200):**
```json
{
  "id": 125,
  "cliente_id": 322,
  "servico": { "id": 8, "nome": "Pilates 1x na Semana" },
  "dias": [
    { "dia": "quinta", "hora": "10:00", "profissional": { "id": 1, "nome": "Pri Savoia" }, "sala": 1, "lotado": null }
  ],
  "valor_mensal": 200,
  "percentual_desconto": 0,
  "dia_vencimento": 15,
  "limite_semanal": 1,
  "horarios": "quinta às 10h"
}
```

| Field | Meaning |
|-------|---------|
| servico | The service the plan is sold as. `nome` is what the studio calls it |
| dias | The weekly grid, one entry per session day, with the assigned professional and room |
| dias[].lotado | Always `null` on a read — the read does not touch the calendar. Only an edit (section 22) resolves it |
| valor_mensal | Monthly value currently charged |
| percentual_desconto | Percentage discount recorded on the plan, `0` when none |
| dia_vencimento | Day of the month the charge is issued (1–31) |
| limite_semanal | Sessions per week the service allows, parsed from its name ("Nx na Semana"). `null` when the name does not follow the pattern |
| aviso | Present only when `limite_semanal` is `null`. Tell the user the limit could not be determined |
| horarios | Short schedule text generated by the proxy, e.g. `"terça e quinta às 9h"`. No professional or room in it — take those from `dias` |

**Removed fields** compared to the previous version of this section: `atendimentos_feitos`,
`atendimentos_repor`, `validade`, `pausado_em`. If the user asks for session counts, use the
attendance endpoints, not this one.

**Errors:** `404` (or whatever 4xx SeuFisio returns) with `{ error, details }` when the plan
does not exist; `500 { error, details }` on upstream failure.

**Use cases:**
- Answering "what is X's plan?" for a recurring plan
- Reading the current grid before editing it (section 22), so you can send the full grid back

### 22. Edit Recurring Plan

Change an existing recurring plan: weekly grid, service type, monthly value, discount and/or
billing day. One call does it all: it reads the plan, applies only the fields you send,
validates the weekly limit, writes the full object back and returns the plan as it is now.

**Request:**
```
PUT {{SEUFISIO_PROXY_URL}}/api/plans/recurring/125
Authorization: Bearer {{SEUFISIO_API_TOKEN}}
Content-Type: application/json

{
  "dia_vencimento": 5,
  "dias": [
    { "dia": "terca",  "hora": "09:00" },
    { "dia": "quinta", "hora": "09:00" }
  ],
  "tipo_atendimento_id": 9,
  "valor_mensal": 335,
  "percentual_desconto": 10
}
```

**Parameters (in body) — every field is optional, but the body cannot be empty:**
| Field | Type | Required | Description |
|-------|------|----------|-------------|
| planId | number | Yes | Plan ID (path) |
| dia_vencimento | number | No | New billing day, 1–31. Writes only the charge day; renewal day and end date are never touched |
| dias | array | No | **The whole new weekly grid**, not a partial change. Same shape as in `POST /api/plans` |
| dias[].dia | string | — | `domingo`, `segunda`, `terca`, `quarta`, `quinta`, `sexta`, `sabado` (no accents) |
| dias[].hora | string | — | `HH:MM` |
| dias[].profissional_id | number \| null | No | **Leave it out.** The proxy assigns from the calendar, as on creation. Send it only when the user asks for a specific professional |
| tipo_atendimento_id | number | No | New service type (from `GET /api/attendance-types`). Changing it also changes the weekly limit and, unless `valor_mensal` is sent, recalculates the price |
| valor_mensal | number | No | Custom monthly value. **Only when the user explicitly asks for a specific value.** It is frozen on the plan |
| percentual_desconto | number | No | Percentage discount, 0–100 |
| raw | `1` | No | Query param. Debug only |

Do not send `sala_id`, `dia_padrao_renovacao`, `data_encerramento`, `inicio_servico` or
`periodicidade` — they are not accepted or not editable through this endpoint.

**How the price behaves** (you never compute it):

| You send | Result |
|---|---|
| `valor_mensal` | That value, frozen, whatever the service |
| `tipo_atendimento_id` without `valor_mensal` | Recalculated from the studio price table for the new service, same rule as creation |
| neither | Unchanged |

**Weekly limit.** The proxy counts the distinct days in `dias` and compares with the
service's `limite_semanal` — the **new** service's limit when `tipo_atendimento_id` is also
being changed. Too many days → `400`, nothing is written, and there is **no confirmation
flag to force it**. When the limit cannot be read from the service name (`limite_semanal`
is `null`), the count is not validated; the response carries `aviso` and you should tell the
user.

**Response (200):** same shape as section 17. `dias[].lotado` is a boolean **for the days you
sent in this request** (the edit consulted the calendar to assign them); when the request
had no `dias`, `lotado` stays `null` like the read.

```json
{
  "id": 125,
  "cliente_id": 322,
  "servico": { "id": 9, "nome": "Pilates 2x na Semana" },
  "dias": [
    { "dia": "terca",  "hora": "09:00", "profissional": { "id": 1, "nome": "Pri Savoia" }, "sala": 1, "lotado": false },
    { "dia": "quinta", "hora": "09:00", "profissional": { "id": 3, "nome": "Amanda Mel" }, "sala": 1, "lotado": true }
  ],
  "valor_mensal": 335,
  "percentual_desconto": 10,
  "dia_vencimento": 5,
  "limite_semanal": 2,
  "horarios": "terça e quinta às 9h"
}
```

`lotado: true` means that class is already at capacity. **The change was saved anyway**
(studio decision, same as on creation). Mention it to the user; do not undo anything.

**Response (400) — invalid body:**
```json
{ "error": "Corpo vazio: informe ao menos um campo para editar (dia_vencimento, dias, tipo_atendimento_id, valor_mensal, percentual_desconto)" }
```
Also for a bad day name, a bad hour format, `dia_vencimento` outside 1–31,
`percentual_desconto` outside 0–100, or a non-numeric id. Fix the payload; do not retry
blindly. A body with only unknown keys counts as empty.

**Response (400) — over the weekly limit:**
```json
{
  "error": "\"Pilates 2x na Semana\" permite no máximo 2 dia(s) por semana; foram pedidos 3.",
  "limite_semanal": 2,
  "dias_pedidos": 3,
  "servico": "Pilates 2x na Semana"
}
```
Nothing was written. Either drop days to fit `limite_semanal`, or — if the user wants more
sessions — change `tipo_atendimento_id` to the matching "Nx na Semana" service in the same
request. Never tell the user there is an override; there is none.

**Response (400) — nobody works at that day/time** (only when `profissional_id` was not
sent):
```json
{
  "error": "Não foi possível definir profissional para todos os dias pedidos",
  "problemas": [
    { "dia": "quinta", "hora": "07:00", "motivo": "Nenhum horário de 07:00 na agenda de quinta (referência 2026-09-11)",
      "horarios_disponiveis": ["08:00", "09:00", "10:00", "15:00"] }
  ]
}
```
Nothing was written. Offer the times in `horarios_disponiveis` and retry. With
`profissional_id` sent, a day/time with no slot is accepted as requested (`lotado: false`)
and there is no 400 for it.

**Upstream errors:** SeuFisio 4xx is passed through with the same status and
`{ error, details }` (e.g. 404 for an unknown plan); 5xx or network → `500 { error, details }`.

**Side effects:** none besides the plan itself. No WhatsApp message is sent, no contract is
regenerated, no charge is created or changed. The next charge follows the new
`dia_vencimento`/`valor_mensal`; charges already issued are untouched — use section 18 for
those.

**Use cases:**
- Moving the client's class to another day or time
- Upgrading from 1x to 2x per week (send the new `tipo_atendimento_id` **and** the two days)
- Changing the billing day
- Applying a permanent percentage discount or a negotiated monthly value

## Edit Recurring Plan Skill — Step-by-Step Flow

When the user wants to change something in a client's recurring plan:

```
1. Find the customer and the plan → GET /api/clients/:id/sales, pick tipoVenda: servico_recorrente
2. Read the plan → GET /api/plans/recurring/:planId
3. Work out what changes → and what must be sent unchanged (the whole grid, if dias changes at all)
4. Check the day count against limite_semanal → change the service too if the user wants more sessions
5. Edit → PUT /api/plans/recurring/:planId
6. Report → from the response, including lotado warnings
```

---

### Step 1: Find the Customer and the Plan

```
GET {{SEUFISIO_PROXY_URL}}/api/clients?search=<name>
GET {{SEUFISIO_PROXY_URL}}/api/clients/<id>/sales
```

Pick the entry with `tipoVenda: servico_recorrente`. If there is more than one active
recurring plan, ask which. If there is only a `pacote_personalizado`, this flow does not
apply — use section 15 for a package schedule change.

---

### Step 2: Read the Plan

`GET /api/plans/recurring/<planId>` (section 17). You need the current `dias`,
`limite_semanal` and `servico` to build the request.

If `aviso` is present, tell the user the weekly limit could not be read from the service
name and that the day count will not be checked.

---

### Step 3: Work Out the Change

- **Grid.** `dias` replaces everything. "Move Tuesday to Wednesday" on a Tuesday+Thursday
  plan means sending Wednesday **and** Thursday. Days without accents, hour as `HH:MM`.
- **Professional.** Do not pick one and do not query the calendar. Send `profissional_id`
  only when the user names someone.
- **Price.** Do not compute it. Send `valor_mensal` only if the user states a value.
- **Billing day.** `dia_vencimento` alone is a valid request.

---

### Step 4: Check the Weekly Limit

Count the distinct days you are about to send. If it exceeds `limite_semanal`, ask the user
before calling: "That is 3 days on a 2x plan. Do you want to move the plan to Pilates 3x na
Semana?" If yes, add `tipo_atendimento_id` to the same request. If the user insists on more
days without changing the service, explain the proxy will refuse it; there is no override.

---

### Step 5: Edit

Call `PUT /api/plans/recurring/<planId>` (section 22).

- **200** → done, move to step 6.
- **400 with `limite_semanal`** → back to step 4.
- **400 with `problemas`** → nobody works at that time; offer `horarios_disponiveis`.
- **400 with only `error`** → the payload is wrong; fix it.
- **404** → the plan id is wrong; go back to step 1.

---

### Step 6: Report the Result

Tell the user, from the response:
- the new schedule (`horarios`) and who is assigned per day (`dias[].profissional.nome`)
- the service (`servico.nome`) if it changed
- the monthly value (`valor_mensal`) and discount (`percentual_desconto`) if they changed
- the billing day (`dia_vencimento`) if it changed
- **any day with `lotado: true`**: say the class is full, the change is saved, and the
  studio may want to review it

Do not promise any message to the client: the edit sends nothing.

## Conversation Examples — Edit Recurring Plan

### Example 1: Change the billing day

**User:** "Change Kelwin's billing to the 5th"

**Assistant flow:**
1. `GET /api/clients?search=Kelwin` → 216; `GET /api/clients/216/sales` → recurring plan 154
2. `PUT /api/plans/recurring/154` with `{ "dia_vencimento": 5 }` → 200, `dia_vencimento: 5`
3. Respond: "Done — Kelwin's plan now bills on the 5th. Schedule and value unchanged: terça e quinta às 9h, R$ 335/month."

### Example 2: Move one day of a two-day plan

**User:** "Move Ana's Tuesday class to Wednesday at 10"

**Assistant flow:**
1. Find client and plan; `GET /api/plans/recurring/<id>` → `dias`: terca 09:00, quinta 09:00; `limite_semanal: 2`
2. Send the **whole** grid: `{ "dias": [ { "dia": "quarta", "hora": "10:00" }, { "dia": "quinta", "hora": "09:00" } ] }` → 200
3. Read `dias`: quarta went to Pri Savoia (`lotado: false`), quinta stays with Amanda Mel (`lotado: true`)
4. Respond: "Moved — Ana is now on quarta às 10h with Pri and quinta às 9h with Amanda. Heads up: the Thursday 9am class is already full, the change was saved anyway."

### Example 3: Too many days for the plan

**User:** "Add Friday 8am to João's plan"

**Assistant flow:**
1. Read the plan → `servico: Pilates 2x na Semana`, `limite_semanal: 2`, `dias`: segunda, quarta
2. **Catch it before calling:** three days on a 2x plan. Ask: "João is on Pilates 2x na Semana. Adding Friday makes 3 sessions a week — do you want to move him to Pilates 3x na Semana? The monthly value changes to the 3x table."
3. User: "Yes"
4. `GET /api/attendance-types` → "Pilates 3x na Semana" is id 10
5. `PUT` with `{ "tipo_atendimento_id": 10, "dias": [ segunda 08:00, quarta 08:00, sexta 08:00 ] }` → 200, `valor_mensal` recalculated
6. Respond with the new service, the three days with their professionals, and the new monthly value from the response.

### Example 4: Nobody works at that time

**User:** "Put Maria on Thursday at 7am instead"

**Assistant flow:**
1. `PUT` with the new grid → **400** with `problemas: [{ dia: "quinta", hora: "07:00", horarios_disponiveis: ["08:00","09:00","10:00","15:00"] }]`
2. Respond: "Nobody teaches on Thursday at 7am. Available on Thursday: 8h, 9h, 10h and 15h. Which one?"
3. Retry with the chosen time.

### Example 5: Negotiated value

**User:** "Set Carla's plan to R$ 250 a month, she negotiated it"

**Assistant flow:**
1. Find the plan; `PUT` with `{ "valor_mensal": 250 }` → 200, `valor_mensal: 250`
2. Respond: "Done — Carla's plan is now R$ 250/month, frozen at that value. The next charge already comes out at R$ 250; charges already issued are unchanged."

# Regras de negócio para gravar na skill

1. **`dias` é a grade inteira.** Sempre leia o plano antes de mandar `dias`, e mande todos
   os dias que devem existir depois da edição, não só o que mudou.
2. **Conte os dias antes de chamar.** Excesso de dias é `400` sem override. Se o usuário
   quer mais sessões, a resposta certa é trocar o `tipo_atendimento_id` na mesma chamada,
   não insistir.
3. **Não calcule preço.** `valor_mensal` só quando o usuário disser um valor. Troca de
   serviço sem valor é recalculada pelo proxy.
4. **Não escolha profissional nem consulte o calendário.** Igual à venda. `profissional_id`
   só quando o usuário nomear alguém.
5. **`lotado: true` não desfaz nada.** Avise, não bloqueie, não tente reverter.
6. **`dia_vencimento` é só o dia da cobrança.** Renovação e encerramento não são editáveis
   pela skill; se o usuário pedir, é manual no SeuFisio.
7. **A edição não manda mensagem nenhuma ao cliente.** Não prometa aviso, não prometa
   contrato novo. Se o studio quiser avisar o cliente, é conversa fora do proxy.
8. **Cobranças já emitidas não mudam.** Valor e dia novos valem da próxima cobrança em
   diante. Cobrança existente se ajusta pela seção 18.
9. **`aviso` na resposta = limite não lido.** Diga ao usuário que a quantidade de dias não
   foi conferida e confira você, pelo nome do serviço.

# Pendências conhecidas

- **O `GET` não traz mais contagem de sessões** (`atendimentos_feitos`, `atendimentos_repor`),
  nem `validade` e `pausado_em`. Se o agente precisar disso, é pelos endpoints de
  atendimentos, não por este.
- **`lotado` no `GET` é sempre `null`.** Só uma edição consulta a agenda. Se o studio quiser
  saber se a turma atual está cheia sem editar, hoje não há endpoint para isso.
- **Só o dia da cobrança é editável entre as datas do plano.** `dia_padrao_renovacao`,
  `data_encerramento`, `inicio_servico` e `periodicidade` ficam fora da skill por decisão
  do studio.
- **O caminho de sucesso do `PUT` não foi verificado contra um plano real**, só contra a
  captura do app web e as validações. Vale um teste com um plano combinado com o studio
  logo após o deploy.
